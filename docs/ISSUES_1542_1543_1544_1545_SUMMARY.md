# BridgeWise Security & Contract Invariant Verifications (#1542, #1543, #1544, #1545)

## Overview
This document outlines the security invariants, failure mitigations, and test suites implemented to address cross-chain safety guarantees across token handling, gas bounds, execution resilience, and timeout refunds.

---

### 1. Invariant Tests for Fee-on-Transfer Tokens (#1542)
- **Challenge**: Standard ERC-20 deposit accounting tracks nominal amounts. For tokens that assess reflection fees or transfer burn taxes, trusting the passed `amount` creates an unbacked vault deficit.
- **Invariant**:
  $$\text{Vault Token Balance} \ge \sum \text{Credited Bridge Obligations}$$
- **Mitigation**: Measure actual differential post-transfer `balanceOf(vault)` and only credit net received funds.
- **Verification**: `test/bridgewise-fee-pause-refund.test.ts` validates that nominal versus actual balances maintain complete vault solvency across deposits and subsequent withdrawals.

---

### 2. Destination Gas Limit Validation (#1543)
- **Challenge**: Relaying bridge calls with an insufficient destination gas allowance leads to unrecoverable message drops or silent stuck transactions on Layer 2 / destination chains.
- **Validation Rules**:
  $$\text{gasLimit} \ge \text{MIN\_EXECUTION\_GAS} + (\text{payloadBytes} \times \text{BASE\_GAS\_PER\_BYTE})$$
  $$\text{gasLimit} \le \text{MAX\_PERMISSIBLE\_GAS}$$
- **Verification**: Tests reject under-budgeted transactions and enforce payload-dependent dynamic gas scaling.

---

### 3. Recipient Contract Revert Containment (#1544)
- **Challenge**: If an arbitrary smart contract recipient reverts on token receipt (e.g., failed callback, reentrancy lock, or out-of-gas in receiver hook), standard atomic transactions fail and freeze the relayer pipeline.
- **Mitigation**: Bridge receiver catches execution exceptions during the final hop, diverting the payload to a secure pull-based escrow rather than reverting the cross-chain settlement.
- **Verification**: Tests confirm reverted deliveries are safely registered into escrow and can be claimed by authorized emergency fallback addresses.

---

### 4. Timeout-based Source Refund Path (#1545)
- **Challenge**: If a destination chain experiences extended downtime, hard forks, or validator halts past the accepted service window, user funds locked on the origin chain must not remain permanently trapped.
- **Mitigation**: Time-locked escrow allowing origin depositors to trigger verified refund redemption after timeout expiration ($T > T_{\text{init}} + \text{TIMEOUT}$), with anti-replay guarantees preventing duplicate payouts.
- **Verification**: Tests enforce strict adherence to expiration boundaries and prevent double-refund attacks.
